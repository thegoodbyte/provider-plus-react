# Medical processing in work modes

PPVC-836 builds on the PPVC-835 foundation. Deploy its API before admin; include PPVC-835 first or in the same release. This ticket is implemented locally and has not been pushed or deployed.

## Staff workflow

1. Open Work modes from Focused work in the sidebar/account menu, enter Medical processing, and start a selected batch, the first five actionable entries, or all actionable entries.
2. Step A shows submitted artifacts needing triage. Open the source editor to inspect the artifact with client/booking context. Select an advisor if known, then Create or reuse MRR, or choose an appropriate pending MRR and Attach artifact. Existing relevant reviews are reused; the backend checks client, booking, stage, ceremony and review type for attachment. A missing advisor can be assigned later in the source editor. No advisor/client message is sent by preparation.
3. New handoff tasks appear under New arrivals. Select the prepared review and Add selected arrivals before moving to B; this explicitly extends the original batch.
4. In B, download review documents or the existing pending packet. Check the downloaded file, send it manually through the normal external WhatsApp process, then choose Record sent via WhatsApp and record the assigned advisor and actual sent date. Downloading alone never marks a review sent and does not advance progress. No delivery confirmation is claimed.
5. An unanswered handoff appears in Waiting on advisor, separate from actionable responses. After an actual reply arrives, use Add to batch and record reply. This explicitly includes the waiting C entry in the batch without marking it actionable or completed. If you cancel, its Record reply entry remains under unresolved batch items.
6. Record advisor reply opens the existing WhatsApp form. Enter answer date, actual result and notes, a reason for recording on the assigned advisor's behalf, and any follow-up flag. Won’t do requires its reason and an explanation for Other. Dates, advisor assignment, notes and delegation are validated by the server. Saving records an existing advisor decision; it does not generate medical advice and sends no notification messages.
7. All five result mappings are preserved: OK → approved; Caution → caution; More information needed → needs_resubmission; Declined → rejected; Won’t do → wont_do. Needs-information/follow-up remains visible for further staff handling through the existing source editor. A recorded answer cannot be overwritten by replaying this work-mode action.
8. Operational review/no further action, Skip and Block remain under the current item's expandable actions. Explicit operational reviews are audited; skip/block reasons and next actions remain unresolved and do not count as completion. Saved medical actions remain linked to their source for later follow-up. Completed by you counts successful staff actions, not independent clinical approval. After editor changes, refresh to reconcile source records. Take a break/resume/reload retains saved progress; the banner returns from editors to the same session.
9. Failed downloads never mark sent. Failed saves keep the form and notes. For an ambiguous save, Check saved review in a new tab keeps the draft open; verify the source before retrying. If the domain save succeeds but progress cannot be saved, the API explicitly instructs refresh and no blind repeat. Source/revision conflicts do not silently advance the form.

## Implementation and concurrency

Medical actions run through owner-scoped work-session routes and require the current session revision and source fingerprint. Only effective admins may act; read-only support sessions cannot write. Waiting replies must be explicitly included in the cohort before acting. The existing MedicalReviewRequestsService performs creation, attachment, manual status recording, delegated review validation, decision history, audit and booking-flow synchronization. Work-mode review calls use an internal notification-suppression policy; no public payload can enable that internal policy or supply server-owned delivery fields.

Creation reserves a canonical preparedReviewRequestId atomically on the source artifact and uses that ID plus the existing unique automationKey to prevent duplicate creation across concurrent create/attach/automation paths that use createFromArtifact. An interrupted create can retry the same reservation. Attachment is additive ($addToSet), requires an appropriate pending unsent review, and rejects conflicting reservations. This does not prohibit deliberate separate attempts through the generic MRR creation API.

Manual sent/reply writes compare the MRR updatedAt value atomically; replies also reject an already-responded source. Session outcome recording follows successful domain persistence and stores only source IDs/action names, never the medical reply notes. Domain and session updates are not a multi-document transaction: a domain success followed by an audit/session failure requires source refresh and reconciliation. Retry guards prevent duplicate MRRs or repeated decisions. Existing domain editors keep their own permissions and notification behavior.

The decision-history/file-review schema now accepts WONT_DO, which was previously accepted by the DTO/result mapper but rejected during persisted history validation. Questionnaire documentType is also aligned with the artifact/DTO type. Food-intake artifacts remain eligible medical review inputs; contracts are excluded from this queue.
